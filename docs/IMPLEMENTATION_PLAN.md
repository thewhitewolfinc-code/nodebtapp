# Nodebt implementation plan

Approved product decisions are recorded in [DEVELOPMENT_READINESS.md](DEVELOPMENT_READINESS.md). This plan orders delivery of the full commercial MVP; only explicitly deferred features are excluded. Continue in the existing repository and keep the lockfile and Git history.

## Architecture and defaults

- Keep Expo 58, React Native 0.88, TypeScript 6 and Expo Router. Non-route domain, storage, integration and UI code stays outside `src/app`. Android/iOS are production targets; browser preview is not a public web product.
- Use a pure TypeScript financial domain with integer paise, immutable transaction revisions, deterministic ledger projections, calendar-date schedules and separate forecasting inputs/results. The validated P0 engine remains the calculation boundary.
- Next add transactional SQLite storage on device. Use a versioned migration history; store original records and all revisions, never just cached balances. Atomically write a financial command and its outbox item. Rebuild read models from validated transactions.
- Protect native storage using SQLCipher with a random device key in SecureStore, tested in development builds. Fail visibly if the required encryption is unavailable. Do not persist real financial records in browser localStorage or silently fall back to an unencrypted database. A browser-only preview may use clearly labeled, ephemeral sample data later.
- Use Supabase Auth/Postgres/Edge Functions for the managed backend, with RLS ownership policies on every exposed user table, scoped server operations and no service keys in the app. Use Google and Apple sign-in, explicit identity linking, and account-scoped local data. Choose an India-near region initially and expand based on measured needs; do not add global replication prematurely.
- Implement a bounded financial outbox protocol with stable operation IDs, expected parent revisions, server acknowledgements, retry with backoff and tombstones. The server is canonical for synchronized state; local committed commands remain available offline until acknowledged. Realtime can signal a refresh but is not a replacement for catch-up sync or conflict handling. Begin without a separate paid sync vendor.
- Use RevenueCat for store-verified Pro and nonconsumable lifetime ad-free entitlements. Store products remain the source of displayed purchase prices. Use AdMob banner placements only after consent/configuration gates pass. These providers remain disabled until configured; never simulate a successful purchase or cloud backup.
- Schedule reminders locally through Expo Notifications; no email, SMS or remote push dependency. Reschedule after verified changes, and suppress reminders for settled/closed records. App Lock uses device authentication with configurable background timeout and privacy overlays.
- Keep baseline crash reporting and operational counters free-tier/budget-limited when integrated. Do not send names, balances, notes, tokens, raw imports, backup passwords or financial screen recordings to monitoring. Product analytics is optional later; core operation cannot depend on it.

## P0 — Repair baseline and implement financial domain (started)

Deliver validated INR parsing/formatting and checked arithmetic; record/opening snapshot contracts; positive principal advances; explicitly posted interest/fee charges; component payments; signed reasoned adjustments; borrowing forgiveness/lending write-offs; full revision chains and conflict errors; independent portfolio totals; paid/settled/written-off/adjusted statuses; closure/reopening; one-time/monthly installment projection with FIFO and explicit allocations.

Acceptance: `npm.cmd run check` passes. Tests cover principal/interest splits, partial/overdue installments, arbitrary additional charges, invalid dates, month-end/leap-year handling, safe-integer limits, duplicate/stale writes, correction/void/restore, settlement versus cash, archived balances, and principal-only prepayments. SDK compatibility passes Expo Doctor. No UI can bypass domain validation when connected later.

## P1 — Encrypted local persistence and guest tracking journeys (Android storage verified; full device acceptance pending)

1. Add SDK-compatible SQLite/SecureStore dependencies, encrypted native development-build configuration, schema version 1 and a transactional repository adapter. Test restart, rollback, interrupted writes, corruption handling and migration recovery before accepting real data.
2. Define records with title, direction, kind, counterparty label, category, INR currency, tracking start, terms/model eligibility, archive/closure metadata and stable IDs. Keep person names private labels with no contacts permission or counterpart invitations. Set flags for unknown interest breakdown/unsupported contracts; planner admission requires validated principal/terms.
3. Define an explicit, versioned command boundary for record creation, posting/correcting/voiding entries, settlement, archive and reopen. Commands include expected revision and idempotency key. Corrections that invalidate later payments or allocations must return actionable errors before commit. Opening snapshot plus related entry components is one atomic command.
4. Extend the existing Router into Home, Records, Activity, Insights and Settings. Preserve starter files/history while replacing their entry points deliberately. New users see a short introduction, guest/sign-in choices and guided first record with skip; returning users reach Home after optional App Lock.
5. Home keeps liabilities and receivables separate; Records supports direction/category/status search and filters; detail shows component balances, due schedule and full activity. Provide explicit repayment/collection, charge, adjustment, forgiveness/write-off and partial-settlement forms. Never show forgiveness as repayment progress.
6. Payment form reviews principal/interest/fees and installment versus principal-only allocation. Explicitly record any newly recognized charge together with its payment. Keep contracted future installments unchanged unless a supported rule recalculates and the user reviews a proposed versioned schedule. Fee payments must not silently satisfy unrelated installments.
7. Seed separate, versioned borrowing (16) and lending (14) catalogs with exactly 6 Free defaults in each direction. Use stable direction-specific IDs; labels are launch defaults, not financial models. Default categories are read-only in P1, and catalog changes after release require a versioned migration. Free exposes exactly 6 borrowing defaults and 6 lending defaults and allows up to 3 custom categories per direction. Pro exposes all 16 borrowing defaults, all 14 lending defaults and unlimited custom categories. Expired Pro users retain existing custom categories and all historical assignments; a downgrade never deletes or relabels records. No destructive category deletion that orphans records.

Acceptance: guest creates a debt and a receivable, records split/partial payments, restarts offline and sees exact same balances/history; missed payment leaves its unpaid portion overdue; edits reproject all affected views. Empty/loading/error states, screen-reader labels, adequate text scaling, tap targets and system light/dark support work. Begin with English and accessible system UI conventions; visual refinements do not block the ledger.

## P2 — Free privacy, reminders, CSV and encrypted recovery

- Implement optional device biometrics/passcode lock, disabled by default. Timeout choices: immediately, 30 seconds or 1 minute. No separate Nodebt PIN when device authentication works. Detect missing device security and explain how to enable it. Verify cold start, foreground resume and authentication cancellation on both platforms.
- Ask notification permission in context. Support per-record reminders for one-time/monthly dues and collections with a default 9:00 a.m. local delivery time, configurable by the user. Keep generic content unless detailed notifications are explicitly enabled. Schedule a rolling OS-supported window; reschedule on edits, payment, closure, timezone changes and foreground reconciliation. Permission denial never blocks tracking. Do not promise exact offline delivery beyond OS support.
- CSV exports are a bundle of records, transactions/revisions, categories and schedule tables linked by IDs, with explicit INR codes, dates and minor-unit columns plus readable amounts. Escape spreadsheet-formula prefixes in user text. Warn that CSV files are plaintext and sensitive.
- Add a versioned, password-encrypted complete backup containing records, all revisions, categories, schedules, relevant settings and calculation model metadata. Use a maintained authenticated-encryption implementation and a password KDF with independently reviewed parameters; never invent cryptography. Random salt/nonce per backup, password confirmation, bounded parsing/KDF settings and no password logging/storage/recovery key.
- Backup data must exclude OAuth sessions, service secrets, device encryption keys, notification permission grants and billing authority. Entitlements must be reverified rather than restored as trusted flags. Security preferences may be included, but device authentication and notification enrollment require consent on the destination.
- Restore stages: bounded file/header validation -> decrypt/authenticate -> schema/version/migration checks -> identity/revision/component/currency validation -> duplicate/conflict review -> explicit confirmation -> atomic import -> verify -> acknowledge success. Failures leave source and destination intact. Import never silently overwrites or resets history. Free users get the complete workflow.

Acceptance: round-trip all supported data including voided/corrected entries, full dates and principal/interest components; wrong password, tampered/truncated/oversized/future-version files fail safely; cancellation/interruption leaves current data intact; notification and lock tests run on real Android/iOS hardware.

## P3 — Accounts, sync, guest migration and deletion

- Configure Supabase project and Google/Apple identities; use a separate nonproduction environment or local Supabase stack and synthetic test data. Track migrations in the repository. Isolate records/revisions/categories/schedules/settings/outbox/device ownership under the authenticated owner; never authorize using editable user metadata.
- Implement push/pull catch-up with persisted cursors and idempotent commands. Acknowledge only after a complete server transaction. Distinct new payments can coexist; two revisions with the same parent create a visible conflict and flag affected totals. Resolve by an explicit revision incorporating the chosen correction, preserving both proposed branches. Do not use last-write-wins for money.
- Test expired sessions, network loss, repeated requests, duplicate webhook/command delivery, server failures and out-of-order responses. Resume on reconnect/foreground and expose pending/synced/needs-attention states. Cloud downtime cannot erase guest/offline work.
- Guest-to-account import displays existing cloud records separately, reviews likely duplicates, preserves every selected record's related history/settings/metadata, and never automatically financial-merges. Use migration/import IDs and per-record acknowledgements to make retry safe. Keep the original guest ledger until verified destination commit; skipping leaves it recoverable and isolated.
- Sign Out protects unsynced work and never exposes one account's cache under another account. Require online account deletion with an export offer and explicit confirmation. Revoke sessions, block writes, purge active data/current-device data and retain minimal deletion/replay protection as appropriate. Old devices cannot re-upload into the deleted identity; cached offline devices are reconciled on reconnect. Explain provider backup retention and applicable retained purchase/legal metadata accurately.

Acceptance: two-device conflict/retry tests; owner A cannot read/write owner B's data; malformed/forged owner IDs fail; deletion racing an upload cannot resurrect data; reconnect after deletion is rejected; guest migration succeeds exactly once after a disconnect.

## P4 — Pro calculators and forecasts

- First support interest-free and disclosed monthly fixed-APR models with integer rounding per month, explicit minimum payments, no new spending/late fees/rate changes unless the chosen scenario models them, and bounded simulation horizons. Undefined/unsupported contracts are trackable but cannot silently enter a forecast. Models must be versioned and results labeled estimates.
- Use eligible borrowing only. Monthly user budget includes all minimum payments; reserve those before allocating extra. Flag insufficient budgets and non-amortizing plans, without claiming a payoff date. Never treat receivables as available repayment cash.
- Snowball orders principal ascending, then APR descending, then stable ID. Avalanche orders APR descending, then principal ascending, then stable ID. Roll freed payments into the next eligible debt within the fixed total budget; show monthly schedules, interest, payoff horizon and inputs/assumptions.
- Consolidation compares selected current debts against a hypothetical fixed-rate replacement using entered APR, term/payment and explicit upfront/capitalized fees. Balance transfer models entered eligible amount, transfer fee, promotional duration/APR and post-promotion APR, with clear assumptions. Neither calculator alters real ledger records or promises lender approval.
- Save immutable scenario input/result snapshots with model version and calculation date. Label snapshots stale after source changes; expired Pro users can view saved results but cannot recalculate/create them. Unit-test against independent hand-computed fixtures, interest-free edge cases, one-paisa remainders and promotion boundaries.

Acceptance: all four tools produce reproducible verified results; zero/insufficient budgets and incomplete terms have clear outcomes; interest/promo rounding cannot hide a residual balance; saved forecasts never become recorded financial facts.

## P5 — RevenueCat subscriptions and AdMob banners

- Set up verified monthly/annual Pro and separate nonconsumable lifetime ad-free products in both stores, with India target prices ₹99/₹699/₹1,499 respectively. Show localized store prices and renewal terms, never a hardcoded price presented as the live checkout amount. Require Nodebt sign-in before purchase; identity mapping survives device/platform changes.
- Pro grants calculators, all 16 borrowing/all 14 lending defaults, unlimited custom categories and advanced forecasts, and removes ads. Free retains 6 defaults plus 3 custom categories per direction. Lifetime ad-free removes ads only. If Pro expires, retain records, existing categories and saved scenarios; disable new premium work. Honor cached verified Pro until paid-through expiry and cached verified lifetime ownership until refreshed; purchases/restoration require connection. No timed trial; sample previews use labeled sample data.
- Verify purchase/refund/renewal/grace/revocation/webhook handling idempotently and reconcile missed events. Client flags never authorize backend premium operations. Restore and subscription-management links are visible. Account deletion explains store subscription management; do not imply deleting Nodebt automatically cancels a store subscription.
- AdMob stays test-only until real app IDs, disclosures and consent behavior pass review. Ads are confined to quiet banner areas on Home/Insights and suppressed for either paid ad-free entitlement. No interstitials, rewarded ads, financial forms, backups/imports or ads while App Lock covers the app. Ad network failure leaves core tracking functional.

Acceptance: sandbox end-to-end purchase/restore, device switch, expiry/refund and independent lifetime ownership tests; no double purchase grants; no Pro accidentally granted by lifetime; no ads for verified ad-free access.

## P6 — Release hardening

- Run domain/forecast tests, typecheck, lint, native release builds and device journey tests; add CI and integration checks as their targets exist. Keep secrets out of Git and client bundles. Recheck npm advisory state without forced SDK downgrades.
- Verify encrypted storage/backup recovery, schema upgrades, bounded inputs, sync replay, RLS, account deletion, privacy overlays, reminders and purchase restoration. Test low-end Android, iOS, denied permissions, background/kill/relaunch, long histories and poor networks. Target responsive local interaction without network round trips; measure on hardware before setting capacity claims.
- Define crash/error/sync-failure alerts without financial payloads, startup and sync timing budgets, backup/restore drills and incident recovery. Launch as controlled store testing before public availability; gate release on the approved full MVP rather than a partially wired screen demo.
- Create EAS development/preview/production profiles when app identities are known. Keep Android/iOS signing credentials managed securely; do not invent final bundle IDs or deploy external state without concrete configuration.

## Cost and setup boundaries

Development uses free tiers where suitable. Public Supabase Pro starts at $25/month before extras and taxes; additional projects, overages, build services and store fees can exceed that amount. Use quotas and alerts and reduce noncritical telemetry/ad requests before restricting core local tracking. RevenueCat's published free threshold is $2,500 monthly tracked revenue, then its current revenue fee applies; reverify before release. No extra always-on API server, paid sync vendor, custom domain, analytics subscription or remote push backend is required initially.

## Approved P1 category and audience correction

- Free: exactly 6 default borrowing categories and 6 default lending categories; up to 3 custom categories per direction.
- Pro: all 16 borrowing defaults, all 14 lending defaults and unlimited custom categories.
- Downgrade preserves custom categories and historical assignments; existing categories remain usable. Creating new custom categories is blocked when the Free limit is already reached, including retained Pro categories. Archiving cannot bypass the limit or erase historical references.
- Initial catalog labels are editable implementation defaults with stable, direction-specific identifiers; the counts and access rules above are approved requirements.
- The audience includes mixed formal/informal borrowers and people who lend money. India/INR is the first configuration, not an assumption embedded in category IDs or ownership architecture.
- P1 does not enable Supabase, paid entitlements, ads or Pro algorithms. Guest access uses the Free policy; Pro/expired-Pro policy is exercised through repository/domain tests, not an unlock toggle in the app.
